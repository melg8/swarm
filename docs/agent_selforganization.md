# Самоорганизация агентов и петли обратной связи в swarm

Ответ владельцу проекта (2026-09-12) на вопрос: как выстроить разработку
swarm силами автономных агентов так, чтобы агенты всегда могли проверить
себя и адекватность своих предположений о протоколе, сервере и
поведении; чтобы качество не уплывало без ревьюера-человека, но и не
тонуло в чрезмерной верификации; и что нужно, чтобы вся система
работала от одного неизменного промпта в направлении «соло 1-60».
Язык документа русский, потому что это ответ владельцу; рабочие файлы
для агентов (`docs/ROADMAP.md`, `docs/BACKLOG.md`) — английские, по
конвенции репозитория.

Документ опирается не на теорию, а на фактическое состояние проекта:
60 раундов агентной разработки в `docs/development_log.md`, живые
acceptance-сценарии, и сегодняшнюю проверку среды (свежий деплой
`swarm_fast_deploy.sh` → STACK_READY, `E2E_OK` от `mobius_e2e.sh`,
19 пакетов тестов зелёные за ~2 минуты). Всё, что здесь описано как
«работает», либо уже есть в репозитории, либо измерено сегодня; всё,
что предлагается добавить, помечено как надстройка и сведено в §9.

## 0. TL;DR

- **Язык: Go**, уже выбранный и подтверждённый практикой (§2).
- **Обратная связь: пирамида верификации L0-L6** с жёсткими бюджетами
  времени и правилом «проверяй то, что тронул» (§3). Оракул «всегда
  под рукой» — исполняемый эталон: локальный сервер Mobius в песочнице
  за ~90 секунд + его Java-исходники + acceptance-сценарии поверх него.
- **Самоорганизация: репозиторий — единственный внешний мозг.** Задача
  столбится коммитом (`docs/BACKLOG.md` с арендой), контекст передаётся
  через `docs/agent_progress.md`, цель разложена в лестницу вех
  (`docs/ROADMAP.md`); промпт запуска не меняется никогда и остаётся
  коротким (§4-5).
- **Прогресс для человека:** лестница вех с бинарными приёмками,
  web UI, soak-метрики прогонов, фиксируемые в git (§6-7).

## 1. Жёсткие ограничения и их следствия для процесса

Процесс обязан работать в этих рамках, поэтому каждое ограничение
переведено в конструктивное требование; в правой колонке — чем оно уже
закрыто в репозитории или чем закрывается надстройкой.

| Ограничение | Следствие для процесса | Чем закрыто |
|---|---|---|
| Песочница агента живёт максимум 2 часа, Linux | Развёртывание среды — один идемпотентный скрипт, минуты, не десятки минут | `tools/swarm_fast_deploy.sh`, ~90 c, повторный запуск безопасен |
| Каждый запуск с нуля (клон + деплой) | Всё состояние проекта живёт в git; ничего ценного в рабочем дереве; зависимости минимальны и кэшируемы | go.mod, генерируемые данные в репе, git-конвенции |
| До 5 агентов параллельно, прямой связи нет | Единственный канал координации — коммиты; нужна явная очередь задач со столблением коммитом | `docs/BACKLOG.md` (новое), rebase-протокол в AGENTS.md |
| Агент может зависнуть или умереть в любой момент | WIP-коммиты часто; у задачи аренда с истечением; resume-заметки в репозитории | протокол аренды (новое), «commit early, commit often» (есть) |
| Человек лишь перезапускает, решает капчу/логин и смотрит прогресс | Промпт запуска постоянен; вся организация внутри репозитория; у человека одна «панель здоровья» | §5, §7 |
| Нельзя чрезмерную верификацию — ждать часы на проверках, не затрагивающих изменение | Пирамида уровней с бюджетами времени; правило «проверяй то, что тронул» | §3; `golangci-lint run --new`, пакетные прогоны |
| Нельзя отпускать качество без ревьюера | Гейты закрытия раунда; храповик «багрепорт → воспроизводимый тест → сценарий» | `task check:all`, acceptance-сценарии, development_log |

Отдельно про капчу и логин. Текущая цель — локальный эмулятор Mobius,
у которого `AutoCreateAccounts = True` и нет капчи: автономия здесь
полная, человек не нужен вообще. Капча появляется только на внешнем
реальном сервере — это поздняя веха, и для неё человеческое действие
концентрируется в один редкий ритуал: живой клиент один раз логинится
через MITM-прокси в режиме записи (`-proxy -proxy-log`), человек решает
капчу руками, а захваченный трафик становится новым ground truth для
всей оффлайн-пирамиды (фикстуры, fake-server, декодеры). Инфраструктура
записи и реплея уже существует (`internal/swarm/proxy/recorder.go`,
`replay.go`), поэтому схема не требует новых механизмов — только
дисциплины «каждая живая сессия оставляет после себя артефакты».

## 2. Выбор языка: Go — и почему это остаётся правильным

Критерии специфичны для агентной разработки, а не для ботописательства
вообще: дорога не производительность, а стоимость ошибки агента и
скорость контура «написал → узнал, что не так → исправил» внутри
двухчасового окна, повторяемого сотни раз.

| Критерий | Go | Rust | C# | Python |
|---|---|---|---|---|
| Ловит типовые ошибки агентов до запуска | да: компилятор, vet, строгий линтер | лучше всех | да | нет, runtime |
| Холодный билд + тесты этого проекта | ~40 c билд, ~2 мин весь suite | минуты на сборку с зависимостями | ~минута + restore | нет билда |
| Насколько LLM пишет язык с первого раза | очень близко к компиляции | хорошо, но итерации дороже | хорошо | отлично, но ошибки поздние |
| Модель конкурентности на 100 ботов | goroutine + `-race` детектор | async/tokio, сложно для агентов | Task/async | GIL |
| Бинарные протоколы | `encoding/binary`, `x/crypto` | nom/serde, сильнее всех | неплохо | struct, хрупко |
| Цена кросс-сессионных рефакторингов | низкая: gofmt + статика | низкая | средняя | высокая |

Итог — Go, по причинам в порядке важности именно для этого процесса:

1. **Самый дешёвый контур обратной связи.** Ошибка компиляции видна за
   секунды, тест одного пакета — за секунды, полный прогон 19 пакетов —
   ~2 минуты (измерено сегодня). В двухчасовом окне это десятки циклов
   на сессию. Холодная сборка с нуля не съедает бюджет сессии — в
   отличие от Rust, где каждая из сотен сессий платит минуты за
   компиляцию зависимостей и борьбу с borrow checker/async.
2. **Линтер навязывает единый стиль.** Строгий `golangci-lint`
   (80 колонок, funlen, cyclop, exhaustruct, godot и т.д.) — это
   замена код-стайл-ревьюера: пять разных агентов с разными «почерками»
   не могут превратить код в нечитаемую смесь, потому что стиль
   определяют инструменты, а не вкус сессии.
3. **`-race` ловит то, что агент не видит глазами.** Главный класс
   невидимых ошибок — гонки — в этом проекте уже всплывал и был
   пойман детектором (см. development_log, волна P01). Для кода,
   который пишет не человек, это обязательный инструмент, а в Go он
   встроен и быстр.
4. **Корпус обучающих данных.** Модели пишут идиоматичный Go почти с
   первого раза; язык мал, «умных ловушек» мало (в отличие от UB в C++
   или lifetimes в Rust).
5. **Стандартная библиотека закрывает ровно нашу задачу:** `net`,
   `crypto` (blowfish), `encoding/binary` (little-endian ридеры),
   `testing` с бенчмарками из коробки, `go:embed` для web UI.

Rust выиграл бы в выразительности парсеров (nom/serde) и гарантиях
памяти, но производительность узких мест уже измерена бенчмарками
(крипт, парсеры, pathfind) и достаточна для 100 ботов (`fleete2e`
гоняет реальный флот против живого стека). Python не годится ядром:
ошибки проявляются в рантайме, а потерянный час 24/7-бота — это ровно
та цена, которую процесс не может платить. C# — рабочий вариант, но
тяжелее бутстрап в песочнице и слабее представлен в обучающих данных.

Отдельное архитектурное решение, дополняющее выбор языка: **поведение —
это данные, а не код.** Зоны охоты, каталоги магазинов, таблица опыта,
npc-данные, системные сообщения генерируются скриптами из датапака
Mobius (`tools/generate_*`). Менять «что делает бот» можно, не трогая
«как устроен бот», и каждая генерация верифицируема повторным прогоном.
Связка «ядро на Go + поведение как генерируемые данные» — правильная
архитектура для разработки агентами: код меняется редко и под
тестами, данные — часто и дёшево.

## 3. Пирамида верификации: как агенты «всегда могут проверить себя»

Центральный принцип: у агента нет права на «мне кажется». У него есть
исполняемый оракул на каждом уровне детализации, и действует правило:
любое утверждение о мире (протокол, сервер, поведение персонажа)
обязано быть либо (1) подтверждено исполняемым артефактом — тестом,
сценарием, измерением, — либо (2) явно помечено как гипотеза с планом
проверки. Сокрытое предположение — это баг процесса, хуже ошибочного
кода, потому что его никто не ищет.

Уровни (время — из сегодняшнего прогона на живом стеке):

| Ур. | Что | Команда | Время | Когда запускать |
|---|---|---|---|---|
| L0 | Компиляция + vet | `go build ./... && go vet ./...` | ~5 c | после каждого изменения |
| L1 | Линт изменённого кода | `golangci-lint run --new` | ~20 c | перед каждым коммитом |
| L2 | Тесты затронутых пакетов | `go test ./internal/swarm/hunt/... -count=1` | 1-35 c | внутри рабочего цикла |
| L3 | Полный юнит-прогон | `go test ./... -count=1` | ~2 мин | закрытие раунда |
| L4 | Fake-server сценарии | `go test ./internal/swarm/connection -run Hunt` | секунды | изменения поведения |
| L5 | Живой e2e против локального Mobius | `tools/mobius_e2e.sh 45` | ~2 мин | изменения соединения/флоу |
| L6 | Acceptance-сценарий цели | `-acceptance farm-readiness` | 10-30 мин | закрытие вехи / по кнопке |

Правило «проверяй то, что тронул» — прямой ответ на требование
исключить чрезмерную верификацию. Внутри цикла запускаются только L0+L1+L2
(затронутые пакеты, по возможности с `-run` фильтром до конкретного
теста). Перед пушем добавляется L4, если менялось поведение, и L5, если
трогалось соединение или прокси. Полный L3 — один раз на закрытие раунда
вместе с `lint --new = 0`. L6 — только на закрытие вехи или по нажатию
человека в TESTS-панели. Экономика типового раунда: 2-3 минуты на
деплой, рабочие циклы по 1-3 минуты верификации, один финальный прогон
5-10 минут. Никогда не запускается «всё подряд» без причины — и в этом
же запрет находится граница качества: гейты раунда прогоняются всегда,
без «мне кажется, не сломал».

Что делает оракул «всегда доступным» — три опоры:

1. **Сервер-как-спека.** Локальный Mobius C1 разворачивается в песочнице
   за ~90 секунд, и его Java-исходники лежат рядом с рабочим деревом.
   Любой вопрос «как сервер реагирует на X» закрывается чтением
   соответствующего Java-класса (`AttackRequest.runImpl`,
   `AttackableAI`, `Player.useEquippableItem`) и/или живым
   экспериментом на локальном стеке с последующим чтением логов. Это
   устраняет главный источник ложных предположений — рассуждение о
   поведении сервера по памяти или интуиции. Правило уже закреплено в
   AGENTS.md: сервер не патчится под бота, бот подстраивается под
   сервер; единственные допустимые серверные патчи — диагностические
   лог-строки (DEATHLOG, GUARDDMG, ATTACKLOG).
2. **Храповик багрепортов.** Каждый живой инцидент, найденный
   пользователем, обязан заканчиваться не «починил», а тремя
   артефактами: repro-юнит-тест, root-cause запись в development_log и
   acceptance-сценарий с DB-инъекцией, восстанавливающий точное
   состояние персонажа из дампа. Образец уже отработан: сценарий
   gear-gap будит аккаунт с точной экипировкой из дампа минус ноги —
   и проходит только когда слот снова занят. После этого класс ошибок
   не может вернуться незамеченным: любая регрессия рвёт сценарий.
3. **Дистиллят проверенных фактов.** AGENTS.md хранит факты с пометками
   «verified live» и разделами «do not re-derive» (измеренные значения
   штрафа опыта, поведение флуд-протектора, семантика Appearing). Новые
   факты добываются диагностическими строками сервера и логами бота и
   с каждой находкой переносятся в AGENTS.md — конституция растёт
   монотонно, ни один раунд не теряет знания.

Чего в пирамиде не хватает и что предлагается надстроить:

- **Реестр гипотез.** Для непроверенных допущений нужна явная площадка
  — раздел «Hypotheses / Unknowns» в профильном документе (образец
  уже есть: `docs/navigation_analysis.md` перечисляет непроверенное о
  плавании, дверях, транспорте). Правило: код, опирающийся на
  гипотезу, обязан ссылаться на её строку; проверка гипотезы —
  отдельная задача в BACKLOG, закрывающая её переводом в «verified»
  с указанием измерения. Так исключается тиражирование непроверенного
  допущения пятью агентами параллельно.
- **Soak-метрики.** Длинные прогоны (часы) должны оставлять
  машиночитаемый артефакт — строку в `runs/metrics.jsonl` (сценарий,
  длительность, стартовый и конечный уровень, XP/час, смерти, адена,
  stuck-события, PASS/FAIL). Это одновременно и корм для прогресс-
  дашборда (§7), и регрессионный детектор: деградация XP/час между
  коммитами видна как дифф файла.
- **Сторож застоя.** Автономный бот 24/7 — это система, которая может
  молча стоять на месте. Контрмера: охота логирует «нет прироста XP
  за M минут» и «позиция не менялась K минут» как явные события, а
  acceptance-сценарий soak проваливается на них. Живой пример
  необходимости: раунд 60 целиком посвящён livelock'у городских
  прогулок, который без такого сторожа просто выглядел бы как «бот
  онлайн, но не качается».

## 4. Самоорганизация: репозиторий как внешний мозг

У системы нет координатора, очереди сообщений и общей памяти между
агентами. Есть внешний мозг из файлов в git, и до пяти
взаимозаменяемых агентов, каждый из которых за своё двухчасовое окно
успевает: развернуть среду, прочитать состояние мозга, взять задачу,
сделать, проверить, задокументировать, запушить.

| Файл | Роль | Кто пишет |
|---|---|---|
| `AGENTS.md` | Конституция: правила, проверенные факты, рецепты | каждый агент, аддитивно и осторожно |
| `docs/ROADMAP.md` | Цель-лестница: вехи с бинарными критериями | владелец + агенты при пересмотре |
| `docs/BACKLOG.md` | Очередь задач: столбление коммитом, аренда, resume-заметки | агенты |
| `docs/agent_progress.md` | Журнал передачи: контекст задачи + прогресс по коммитам | владелец активной задачи |
| `docs/development_log.md` | Память о корнях проблем, 60 раундов | закрывающий раунд |
| `docs/protocol_description.md` | Спека протокола со ссылками на Java-классы | агент, трогающий пакеты |
| `internal/swarm/acceptance/` | Исполняемые цели (сценарии) | закрывающий веху |
| `runs/metrics.jsonl` | Soak-метрики прогонов | сам процесс бота (надстройка) |

Протокол столбления задачи (claim by commit):

1. `git pull --rebase`; выбрать из BACKLOG верхнюю задачу со статусом
   todo, чьи зависимости done.
2. Сменить статус на in_progress, вписать агента и время, закоммитить и
   запушить немедленно. Столбление — это коммит; арбитр гонок — сам
   git: чей пуш прошёл первым, тот и владеет задачей.
3. Если пуш после fetch+rebase обнаруживает, что задачу уже забрали —
   выбрать следующую. Конфликт интересов на файле задачи решается
   тем же механизмом, что и любой другой конфликт в ветке.
4. Аренда: in_progress без прогресс-записи старше 4 часов (по времени
   коммитов в agent_progress.md) считается брошенной; любой агент может
   перезаписать claim, предварительно прочитав resume-заметки. Четыре
   часа — это две сессии: меньше нельзя (убьём живую работу), больше
   нельзя (зависший агент заморозит задачу на сутки).
5. Закрытие: статус done, краткий итог; при частичной работе —
   resume-заметки «откуда продолжать», по которым следующий агент
   стартует без передисковеринга.

Стоп-протокол (последние ~20 минут сессии — неприкосновенны):

- запушить всё, включая незавершённое (WIP-коммиты — норма, а не
  стыд);
- обновить agent_progress.md: что сделано, что осталось, откуда
  продолжить;
- обновить аренду задачи в BACKLOG либо пометить blocked с точной
  причиной;
- никогда не «доносить» работу локально в следующую сессию —
  следующей сессии не будет, будет новый агент с чистой песочницей.

Разрешение конфликтов при пяти агентах в одной ветке:

- задача декларирует scope (пакеты/файлы); вне scope — не трогать;
  кросс-файловые изменения выносятся в отдельные задачи;
- коммиты атомарные и мелкие — конфликт мал и решается честно по
  поведению обеих сторон (правило уже в AGENTS.md);
- история линейная: fetch + rebase + push; никаких merge-коммитов,
  никакого force-push;
- журнальные файлы (agent_progress.md, BACKLOG.md) пишутся только
  аппендами в собственный раздел — это снимает 90% конфликтов на
  самых горячих файлах.

Почему это самоподдерживается без принуждения: положительное
подкрепление агента — зелёные тесты и PASS сценария, приходящие за
минуты; отрицательное — красный прогон перед пушем, который нельзя
обойти гейтом. Человек-судья в контуре не нужен; он появляется только
на приёмке вех и разборе живых инцидентов.

## 5. Промпт запуска: один на всех агентов, неизменный

Промпт короткий, потому что вся организация живёт в репозитории. План
не в промпте — план в ROADMAP и BACKLOG, знания — в AGENTS.md и
development_log, состояние — в agent_progress.md. Промпт лишь запускает
цикл и задаёт дисциплину; меня он не меняет, поэтому человек может
перезапускать агентов механически, одним и тем же текстом:

```text
Ты — автономный агент-разработчик проекта swarm (out-of-game L2-бот на Go).
Репозиторий: https://github.com/melg8/swarm, ветка feature/proxy-server,
коммить как melg8 (public.melg8@gmail.com). Бюджет сессии 2 часа, Linux,
окружение полностью локальное. Другие агенты работают в той же ветке
параллельно.

1. bash tools/swarm_fast_deploy.sh — дождись STACK_READY (идемпотентно,
   ~90 c). Не начинай работу на неразвёрнутом стеке.
2. Прочитай AGENTS.md целиком — это конституция. Затем хвост
   docs/agent_progress.md, docs/BACKLOG.md, docs/ROADMAP.md.
3. Возьми верхнюю todo-задачу из BACKLOG.md (зависимости done; задача с
   просроченной арендой — можно перехватить по resume-заметкам).
   Застолби её коммитом: статус in_progress + агент + время, запушь.
4. Работай циклами: гипотеза → мелкие коммиты → проверка ТОЛЬКО
   затронутого (go build, golangci-lint run --new, тесты затронутых
   пакетов; всё зелёное перед каждым пушем). Перед пушем: git fetch +
   rebase + push. Никаких merge-коммитов, никакого force-push.
5. Никогда не угадывай поведение сервера: читай Java-исходники Mobius
   в песочнице и проверяй живым экспериментом на локальном стеке.
   Непроверенное допущение — в реестр гипотез с планом проверки.
6. Изменения поведения или протокола подтверждаются живой проверкой:
   tools/mobius_e2e.sh 45 или -acceptance <сценарий>.
7. Закрывая раунд: запись в docs/development_log.md (проблема → причина
   → фикс → проверка) и agent_progress.md; баг пользователя превращай в
   repro-тест + acceptance-сценарий.
8. Не трогай файлы вне scope задачи. Застрял — пометь blocked с точной
   причиной и возьми следующую. Никогда не жди решения человека.
9. Цель — автономная прокачка соло 1-60 (лестница в ROADMAP.md);
   каждая задача обязана двигать текущую веху.
10. Последние 20 минут сессии: останови кодирование, запушь всё,
    обнови agent_progress.md, аренду задачи и resume-заметки.
```

Свежий агент становится продуктивным через ~5 минут после старта:
деплой идемпотентен, конституция читается один раз, задачи лежат
готовые. Дальше он трудится сам, потому что: (а) следующий шаг всегда
виден — BACKLOG упорядочен, ROADMAP держит направление; (б)
правильность всегда проверяема локально за минуты (§3); (в) память
проекта целиком считывается из git, ни от кого не зависит; (г) его
смерть в любой момент ничего не рушит — худшее, что теряется, это
незапушенные минуты работы.

## 6. Лестница вех «соло 1-60» (сводка)

Полная версия с критериями приёмки — `docs/ROADMAP.md`. Сводка:

| Веха | Бинарный критерий |
|---|---|
| M0 | Автономная охота в эльфийских землях: гир, магазин, скиллы, города, делевел (готово: farm-readiness PASSED) |
| M1 | Soak: непрерывный прогон 1→20 без вмешательства, метрики в runs/, стабильный XP/час, нет застоя |
| M2 | Первая профессия: квест смены класса на 20 сдан ботом автоматически |
| M3 | 20→40: зоны 20+, учителя, гир второго тира |
| M4 | Вторая профессия (40) сдана автоматически |
| M5 | 40→60: финальные зоны |
| M6 | Интегральный прогон 1→60 без человека (многодневный soak, дашборд) |

Дисциплина вех: веха закрывается только живым acceptance-прогоном,
никогда «кодом написан»; прогресс проекта = самая высокая зелёная веха;
задачи из BACKLOG обязаны ссылаться на веху. Пати, рейды и осады —
следующая лестница (цели зафиксированы в `docs/project_description.md`),
но в эту они сознательно не включены: solo-лестница обязана закрыться
первой, потому что она же строит всю инфраструктуру квестов и зон.

## 7. Наглядная обратная связь для человека

- **Web UI (есть):** карта мира с ботами, HUD, чат, пути, зоны; панель
  TESTS с кнопками acceptance-сценариев — живая картина того, что бот
  делает прямо сейчас, без чтения кода.
- **PROGRESS.md (надстройка):** автогенерируемая страница-сводка:
  лестница вех (зелёная/красная по последним прогонам), последние
  soak-метрики, активные задачи BACKLOG, последние коммиты. Одна
  страница = здоровье проекта; человек смотрит её, а не грепает логи.
- **runs/metrics.jsonl (надстройка):** каждая строка — итог прогона
  (дата, сценарий, длительность, уровни, XP/час, смерти, адена,
  PASS/FAIL). Файл в git: дифф между коммитами показывает тренд
  эффективности бота — деградация видна сразу.
- **Отчёт раунда (правило надстройки):** каждая запись в
  agent_progress.md открывается одной строкой «что стало ближе к цели»
  — чтение одного хвоста файла показывает движение к 60-му уровню.
- **Коммит-стрим:** конвенция сообщений (`area: суть`) делает историю
  читаемой как журнал работ; частота коммитов сама по себе пульс
  проекта.

## 8. Типовые сбои процесса и контрмеры

| Сбой | Контрмера |
|---|---|
| Агент завис, задачу не отдаёт | Аренда 4ч истекает — задача перехватывается по resume-заметкам |
| Два агента взяли одну задачу | Столбление коммитом; git отклоняет второй пуш — агент берёт следующую |
| Ложное предположение о сервере | Запрет угадывания: Java-исходники + живой эксперимент; гипотезы в реестре с планом проверки |
| Тихое «бот стоит, не качается» | Сторож застоя (нет XP M минут) + soak-сценарий падает на застое |
| Чрезмерная верификация съела сессию | Правило «проверяй то, что тронул»; бюджеты уровней; полный прогон только на закрытии |
| Качество уплывает без ревьюера | Гейты раунда (build+vet+полный suite+lint --new=0), храповик багрепортов, `-race` |
| Конфликты в одной ветке | Мелкие атомарные коммиты, scope задач, аппенд-журналы, rebase-протокол |
| Ветки знания расходятся между агентами | Единственный источник — AGENTS.md; каждая находка сразу коммитится в конституцию |

## 9. Что добавляет этот коммит

- `docs/agent_selforganization.md` — этот документ: обоснование языка,
  пирамида верификации, протокол самоорганизации, промпт запуска,
  обзор прогресса, таблица сбоев.
- `docs/ROADMAP.md` — лестница вех «соло 1-60» с бинарными критериями
  приёмки (M1-M6 после текущего M0).
- `docs/BACKLOG.md` — очередь задач с протоколом столбления/аренды и
  посевными задачами под веху M1 и смежную инфраструктуру.
- `AGENTS.md` — указатель на ROADMAP и BACKLOG в рабочем протоколе:
  откуда брать работу, когда agent_progress не содержит активной
  задачи.
